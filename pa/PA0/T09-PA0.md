## 2 Project Idea Overview

### 2.1 Project Name and One-Sentence Pitch

CampusBorrow – a web application that lets students and club representatives submit equipment loan and room booking requests, while giving resource managers a single interface to approve, hand over, and record returns.

### 2.2 Problem and Motivation

Campus units currently manage equipment loans and room bookings through Google Forms, chat messages, and spreadsheets. This leads to:

- No real-time view of equipment availability or room schedules.
- Two students can request the same item simultaneously with no conflict check.
- Equipment status must be updated manually - prone to stale data and errors.
- Overdue loans surface only when a manager audits the spreadsheet.
- Approval history (who approved, when, why rejected) is not structured.
- Room double-bookings occur when requests come through separate channels.

CampusBorrow consolidates catalogue, request lifecycle, and history into one role-based system.

### 2.3 Target Users

| **User Group** | **What They Need from the System** |
|---|---|
| **Borrower (Student / Club Representative)** | Browse equipment and room availability; submit, track, and cancel requests; view personal history. |
| **Resource Manager** | Process requests for assigned equipment/rooms; record hand-over and return; monitor overdue loans. |
| **Admin** | Create/deactivate accounts; assign roles and resources; view all requests and history unit-wide. |

### 2.4 Main Features

Must-have features (F01–F09) must be fully implemented by PA5. F10 is a nice-to-have attempt only if scope is completed early.

| **#** | **Feature** | **Short Description** | **Must-have?** |
|---|---|---|---|
| **F01** | Authentication & RBAC | Three roles: Borrower, Resource Manager, Admin. Accounts created by Admin only; all permission checks on the server. | Yes |
| **F02** | Equipment & Room Catalogue | Searchable list of equipment and rooms. Managers edit assigned resources; Admin manages all. Rooms show capacity and availability. | Yes |
| **F03** | Equipment Borrow Request & Approval | One item per request; requester states purpose and return date. Manager approves or rejects; approval reserves the item atomically. | Yes |
| **F04** | Hand-over, Return & Overdue | Manager records hand-over and return times; system updates availability. Loans past deadline appear in an overdue list. | Yes |
| **F05** | Room Schedule View | Shows approved booking slots for a chosen room on a given day so requesters can find a free slot. | Yes |
| **F06** | Room Booking Request | One room, one day; requester enters start/end time, purpose, and headcount. The system checks time order, future date, and capacity. | Yes |
| **F07** | Room Booking Approval & Conflict Check | Manager approves or rejects; approval blocks if an approved slot overlaps. Requesters can cancel before start time. | Yes |
| **F08** | Request & History Tracking | Borrowers see their own requests; Managers see their scope; Admin sees all. Every action logged with actor, outcome, reason, and time. | Yes |
| **F09** | Global Administration | Admin creates/deactivates accounts, assigns roles, assigns resources to managers. Deactivation does not erase history. | Yes |
| **F10** | Usage Statistics & CSV Export | Usage summary per resource; export borrow/booking list to CSV. | No – Nice-to-have |

### 2.5 Similar Products

**Snipe-IT (snipe-it.readme.io):** Full IT-asset management with multi-location, depreciation, and LDAP. CampusBorrow is scoped to one unit, two resource types, and a simple three-role approval flow.

**MRBS – Meeting Room Booking System (mrbs.sourceforge.io):** Room-only scheduling, often self-service. CampusBorrow combines equipment and room booking under a manager-approval workflow suited to shared academic resources.

**Google Forms + Spreadsheet:** The current practice in most campus clubs. No real-time availability, no conflict prevention, no structured audit trail. CampusBorrow directly replaces this workflow.

### 2.6 Platform and Technology Ideas

Not final; to be confirmed at PA1.

- Platform: web application (responsive); no separate mobile app.
- Frontend: React.
- Backend: Node.js / Express (or equivalent).
- Database: PostgreSQL – transactions and conditional unique constraints for conflict prevention.
- Version control: Git / GitHub with pull requests and CI (GitHub Actions).
- Deployment: Render or Railway for the demo; finalised at PA1.

### 2.7 Feasibility, Scope and Open Questions

Feasibility: F01–F09 are primarily CRUD flows plus two state machines (equipment lifecycle, room booking lifecycle). The hardest part is the atomic approval-and-reserve step (F03/F07). With 4 members working 8–10 h/week over three coding weeks (Wk 8–10), the scope is feasible if the team finishes the core borrow/booking flow before auxiliary features.

**Out of scope:**

- academic timetable integration; event registration;
- recurring bookings;
- multiple items/rooms per request;
- advance equipment scheduling; waitlists;
- maintenance tracking; monetary transactions;
- automated email/SMS; SSO; multi-campus deployment;
- native mobile app.

**Main risks:**

- (1) two managers approving the same resource simultaneously → use DB transactions;
- (2) time-boundary edge cases → standardise on UTC+7, test all boundaries;
- (3) scope creep → freeze Must-have list after PA1.

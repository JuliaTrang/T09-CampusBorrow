# 4.6 Design Principles and Patterns (#54)

These principles apply to the [class diagram](4.2-class-diagram.md), the [class specifications](4.3-class-specifications.md) and the [sequence diagrams](4.4-sequence-diagrams.md). The table describes the intended design. It does not claim that an implementation already follows it; the open points in the [README](README.md) remain.

| Principle or pattern                          | Where it is applied                                                                                                                                  | How and why                                                                                                                                                                                                                                                                                                     | Evidence needed when final                                                                                                                    |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Layered architecture / separation of concerns | CTN-01; controller → service → PrismaService in CTN-02                                                                                               | The UI handles input and output, controllers receive and validate HTTP input, services decide business rules, and the database keeps the concurrency invariants. No business rule lives only in the UI.                                                                                                         | CD-01 and SD-01 – SD-05; code review in PA4                                                                                                   |
| Single Responsibility                         | SessionGuard and RolesGuard (CMP-01), TimetableService (CMP-05), HistoryService (CMP-06)                                                             | SessionGuard checks the session, RolesGuard checks the role, TimetableService derives the interval and HistoryService writes and reads the audit trail. Ownership and business mutations stay in the matching services.                                                                                         | Separate tests for JWT, token version, denylist, role, period and history; no class added without need                                        |
| Dependency Injection                          | EquipmentRequestService uses PrismaService, Clock and HistoryService; RoomBookingService uses TimetableService                                       | Uses the built-in NestJS injection. A fixed Clock can replace the real one in boundary tests, and rollback can be tested when history fails. No service locator or hand-made singleton.                                                                                                                         | Constructor injection; tests for the expiry equality and for save failures                                                                    |
| DRY for time rules                            | Clock (CMP-09), `EquipmentRequest.effectiveExpiry`, TimetableService                                                                                 | One source of server time and one expiry formula; intervals derive from the Period table. The formula is not repeated independently in the client, the job and the handover.                                                                                                                                    | All flows use the same cut-off; TODO-OPS decides the final method location                                                                    |
| Guard / centralised authorisation             | SessionGuard, RolesGuard on protected controllers; ownership in EquipmentRequestService, RoomBookingService and HistoryService                       | Every protected call is checked, and authority is rechecked inside mutations. The role and `borrowerId` from the client are never trusted. An RM has unit-wide access (BR-01).                                                                                                                                  | Tests: direct request, inactive or revoked session, wrong role, another Borrower; ADR-003, DG-03, DG-04                                       |
| Transaction / Unit of Work with Prisma        | `EquipmentRequestService.decide` and `handover`, `RoomBookingService.submit` and `decide`, `HistoryService.append(event, tx)`                        | State, reservation and audit change together (DG-01, DG-06). It reuses `Prisma.$transaction` and adds no wrapper or repository pattern. SQL locks and the exclusion constraint (ADR-004) keep the invariants under a race.                                                                                      | Race between two approvals; a history failure rolls back; no overlap or duplicate loan; `append` uses the caller's transaction (ADR-002)      |
| Optimistic concurrency (version check)        | `version` on Resource, EquipmentRequest and RoomBooking; `expectedVersion` in `EquipmentRequestService.decide` and `RoomBookingService.decide`       | An update runs `WHERE id = ? AND version = ?` and increments `version`. If no row changes, the API returns 409 "record changed – reload" and writes no history (ADR-004, DG-02, BR-17). Row locks and the exclusion constraint handle competing approvals; the version check handles saves from a stale screen. | Test: a save from a stale screen returns 409 and keeps the newer record; screens S05, S09 and S14 show the reload message; FR-02-14 is Should |
| Acyclic module dependencies                   | AuthModule, EquipmentLoanModule, RoomBookingModule and CorrectionModule → AccountModule; AccountModule → HistoryModule; HistoryModule → CommonModule | Following ADR-002, other modules read accounts only through `AccountService.findByIdentifier` and `findById`; AccountModule increments `tokenVersion` itself (ADR-003) and does not import AuthModule. HistoryModule does not call business modules to write events.                                            | The import graph has no cycle; no `forwardRef` hides a cycle                                                                                  |
| Append-only audit                             | HistoryEvent and HistoryService (CMP-06), CorrectionService (CMP-07)                                                                                 | A correction creates a new event that keeps the before and after state, the actor and the time. It never edits or deletes earlier evidence and never stores credentials.                                                                                                                                        | DM-01 (merged) fixes the concepts and #49 confirms the schema; CO-01 – CO-04 come from BR-20 in PA2 v2 and are Should priority                |

No Strategy, Factory, Observer or State pattern is added only to reach a pattern count. The PA3 template requires state machine diagrams (§4.5), but there is no evidence that State objects are needed in code; enums and validation follow the design the team fixes.

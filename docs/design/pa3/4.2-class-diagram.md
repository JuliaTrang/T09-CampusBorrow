## Reading the diagrams

- `+` public, `-` private. `Id`, `Instant`, `Tx`, `Principal`, `Decision`, `Result`, `Interval`, `BookingInput` and `Schedule` are conceptual types used to read the diagram; they are not DTO or code names.
- `Instant` is a server time stored as `timestamptz` and shown in UTC+7. `Tx` is the Prisma transaction context.
- A solid arrow from a controller to a service means "calls". A dashed arrow between services means "uses". Every module also uses CMP-09 (`PrismaService`, `Clock`); those arrows are not drawn.
- Return messages in the sequence diagrams show data or results. They are not extra operations.

## Classes and operations

| Component                  | Classes                                             | Main operations and scope                                                                                                                                                                                                       |
| -------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CMP-01 AuthModule          | AuthController, AuthService                         | `login(identifier, password)`, `logout(cookie)`. The controller forwards the call. The JWT carries `jti` and `tv` (ADR-003).                                                                                                    |
| CMP-01 AuthModule          | SessionGuard, RolesGuard                            | `canActivate(cookie)` returns a Principal or denies. `authorize(principal, allowedRoles)` returns allow or deny.                                                                                                                |
| CMP-02 AccountModule       | AccountController, AccountService                   | `changeSecurity(accountId, change)`. Increments `tokenVersion` in the same transaction (ADR-003). BR-08: the last active Admin cannot be removed.                                                                               |
| CMP-03 CatalogModule       | ResourceController, ResourceService                 | `getEligibility(resourceId, tx)`. Visibility, operational status and occupancy are three separate concepts.                                                                                                                     |
| CMP-04 EquipmentLoanModule | EquipmentRequestController, EquipmentRequestService | `decide(requestId, decision, expectedVersion, actor)`, `handover(requestId, actor)`, `expireIfDue(resourceId, tx)`. Approval and handover use the current state.                                                                |
| CMP-05 RoomBookingModule   | RoomBookingController, RoomBookingService           | `submit(input, actor)`, `decide(bookingId, decision, expectedVersion, actor)`, `getSchedule(roomId, date, actor)`. A Pending booking does not hold the room. The schedule shows staff fields only to an RM or Admin (FR-05-06). |
| CMP-05 RoomBookingModule   | TimetableService                                    | `deriveInterval(bookingDate, firstPeriod, lastPeriod)` returns an Interval. Periods P1 – P8 are fixed (BR-03, C-08).                                                                                                            |
| CMP-06 HistoryModule       | HistoryController, HistoryService                   | `listVisible(actor, query)`, `append(event, tx)`. Never stores tokens or passwords.                                                                                                                                             |
| CMP-07 CorrectionModule    | CorrectionController, CorrectionService             | `correct(input, actor)`. Corrections CO-01 – CO-04 follow BR-20 (PA2 v2, PA3 §8 item 4) and are Should priority.                                                                                                                |
| CMP-08 SchedulerModule     | ExpiryJob                                           | `run()`. For each item with an overdue pickup it calls `expireIfDue(resourceId, tx)`, the same logic as the endpoints (ADR-005, Proposed).                                                                                      |
| CMP-09 CommonModule        | PrismaService, Clock, HttpExceptionFilter           | `$transaction(work)` (inherited from Prisma), `now()`, `catch(error)`. No repository wrapper is added.                                                                                                                          |

The remaining controllers expose the same operations as their services. The sequence diagrams draw calls at the service boundary for brevity; a controller lifeline must use the operations declared in CD-01.

## Entities

| Entity                    | Used by   | Main attributes and invariants (kickoff glossary)                                                                                                                                                                                                                                |
| ------------------------- | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Account                   | CMP-01/02 | username, email, displayName, passwordHash, role, status (AccountStatus), tokenVersion. Exactly one role. Accounts that acted in history are never deleted.                                                                                                                      |
| RevokedToken              | CMP-01    | id (the `jti`), accountId, expiresAt. Created at logout as a denylist entry; it is not a session table. ExpiryJob deletes expired rows (ADR-005, Proposed).                                                                                                                      |
| Resource, Equipment, Room | CMP-03    | Resource (abstract): code, type, name, location, description, visibility, operationalStatus, outOfServiceReason, version. Room adds capacity.                                                                                                                                    |
| EquipmentRequest          | CMP-04    | resourceId, purpose, proposedPickupAt, confirmedPickupAt, returnDueAt, status, decidedBy/At, handedOverAt/By, returnedAt/By, cancellationCause. Expiry and Overdue are computed, not stored.                                                                                     |
| RoomBooking               | CMP-05    | resourceId, bookingDate, firstPeriod, lastPeriod, startAt, endAt, headcount, purpose, status. A Pending booking creates no reservation. An overlapping approved booking is blocked by the database.                                                                              |
| Period                    | CMP-05    | code (P1 – P8), session (DaySession), startTime, endTime, seq. A fixed table of 8 rows.                                                                                                                                                                                          |
| HistoryEvent              | CMP-06    | eventType, actorId (NULL = SYSTEM), actorRole, targetType, targetId, fromState, toState, reason, details, occurredAt. Append-only; never contains credentials.                                                                                                                   |
| StateCorrection           | CMP-07    | operationCode (CO_01_VOID_HANDOVER, CO_02_VOID_RETURN, CO_03_FIX_EVENT_TIME, CO_04_VOID_ROOM_APPROVAL), adminId, targetType (EQUIPMENT_REQUEST or ROOM_BOOKING only), targetId, before, after, reason, appliedAt. Each correction also creates a HistoryEvent `STATE_CORRECTED`. |

Enumerations are used exactly as in the kickoff: EquipmentRequestStatus (PENDING, APPROVED, REJECTED, CANCELLED, ON_LOAN, RETURNED), RoomBookingStatus (PENDING, APPROVED, REJECTED, CANCELLED), AccountStatus (ACTIVE, INACTIVE) and DaySession (MORNING, AFTERNOON). The state machines (#52) and the CHECK constraints (#49) use the same sets. Expired and Overdue are computed values and are not stored.

## Multiplicities (from DM-01 §5)

| Association                                    | Multiplicity                                                    |
| ---------------------------------------------- | --------------------------------------------------------------- |
| Account — EquipmentRequest (borrower)          | 1 — 0..*                                                        |
| Equipment — EquipmentRequest                   | 1 — 0..* (at most one APPROVED or ON_LOAN at once)              |
| Account — RoomBooking (borrower)               | 1 — 0..*                                                        |
| Room — RoomBooking                             | 1 — 0..* (approved intervals never overlap)                     |
| RoomBooking — Period (firstPeriod, lastPeriod) | 0..* — 1, each                                                  |
| Account — HistoryEvent (actor)                 | 0..1 — 0..* (no actor = SYSTEM)                                 |
| HistoryEvent — target                          | exactly one of Account, Resource, EquipmentRequest, RoomBooking |
| Account — StateCorrection (admin)              | 1 — 0..*                                                        |
| StateCorrection — target                       | exactly one EquipmentRequest (CO_01–03) or RoomBooking (CO_04)  |
| StateCorrection — HistoryEvent (primary)       | 0..1 — 1 (`STATE_CORRECTED`)                                    |
| Equipment, Room — Resource                     | complete and disjoint generalisation                            |

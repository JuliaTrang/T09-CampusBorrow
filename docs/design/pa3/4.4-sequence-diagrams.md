## Transactions and queries handed over to #49 and #55

`PrismaService.$transaction(work)` is the API inherited from Prisma; no repository is added. The name inside the brackets describes the group of operations needed; it is not a claim that such a method exists. The notes in each figure state which reads and writes happen before the commit. `HistoryService.append(event, tx)` uses the same transaction, and a failed append must roll back the matching state change. ADR-004 fixes Prisma READ COMMITTED, locking the `resources` row first for equipment, conditional updates on version and state, and 409 on conflict. The exact coordination when a room request is submitted must be checked against #49.

## Review notes before freezing

- SD-01 follows ADR-003 (Accepted); Trang's document records I-05 as closed. No token or password is written to history.
- SD-02: approving for an inactive borrower can still be valid; only handover needs an active borrower. Reject requires a reason of 1 – 500 characters (kickoff, S05 and S09).
- SD-03: a Hidden item does not by itself forbid handover, but In service and the pickup window are still required. At exactly the expiry time the handover is refused even if the stored label is still Approved. A loan already handed over is never released by the job.
- SD-04: the interval is derived from the Periods; `start`, `end` and `borrowerId` from the client are not trusted. Periods P1 – P8 are fixed (C-08); the schema waits for #40 and #49. The submission transaction must coordinate with room approval to recheck conflicts; the serialisation method waits for #49.

When a handover meets a request that has just expired, the team must define the refusal result so the flow does not wrongly roll back the expiry update and its audit entry.

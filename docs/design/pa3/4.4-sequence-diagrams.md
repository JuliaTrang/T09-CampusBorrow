## Transactions and queries handed over to #49 and #55

`PrismaService.$transaction(work)` is the API inherited from Prisma; no repository is added. The name inside the brackets describes the group of operations needed; it is not a claim that such a method exists. The notes in each figure state which reads and writes happen before the commit. `HistoryService.append(event, tx)` uses the caller's transaction and never commits itself (ADR-002, Accepted), so a failed append rolls back the matching state change. ADR-004 fixes Prisma READ COMMITTED, locking the `resources` row first for equipment, conditional updates on version and state, and 409 on conflict. A room submission needs no extra lock: a Pending booking reserves nothing, and the exclusion constraint decides at approval (ADR-004).

## Review notes before freezing

- SD-01 follows ADR-003 (Accepted); Trang's document records I-05 as closed. No token or password is written to history.
- SD-02: approving for an inactive borrower can still be valid; only handover needs an active borrower. Reject requires a reason of 1 – 500 characters after trimming (FR-03-07). A due expiry of another request on the item is applied before the approval is checked; a later business refusal keeps it (4.3 C2).
- SD-03: a Hidden item does not by itself forbid handover, but In service and the pickup window are still required. At exactly the expiry time the handover is refused even if the stored label is still Approved. A loan already handed over is never released by the job.
- SD-05: reject needs a reason of 1 – 500 characters after trimming (FR-07-02, BR-05). An overlap or a stale version leaves the booking PENDING and returns 409 (FR-07-03, FR-07-04); Pending bookings do not block each other.
- SD-04: the interval is derived from the Periods; `start`, `end` and `borrowerId` from the client are not trusted. Periods P1 – P8 are fixed (C-08) and stored in `periods` (ERD-01). An approval that commits while a request is being submitted may leave a Pending request that overlaps it; this holds no room, and approving it later fails on the exclusion constraint with 409 (FR-07-03, ADR-004).

## Expiry met during a handover

ADR-005 calls the expiry logic inside the locked transaction (drawn in SD-03) and uses the same logic for the sweep. Its amendment of 22 November states the refusal result: when a handover meets a request that has just expired, the transaction commits the expiry (CANCELLED, `SYSTEM_EXPIRY`, history event) and the API returns 409 without a loan. The refusal is a result of the committed transaction, not an exception that rolls it back. Only a persistence or history failure rolls everything back (FR-03-15, BR-04, UC-13 E1).

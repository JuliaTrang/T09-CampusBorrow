# PA2 SRS – draft for WBS 2.2.6 and 2.2.9

Paste-ready rows for the PA2 SRS template. WBS 2.2.6 fills the F05 and F06 rows of §5.1 (Table 3). WBS 2.2.9 fills §5.2 (Table 4). Sources: PA1 final (§2.1 Problem Statement, §2.4 scope, §3.3 environment, §5 risks), WBS 2.2.6 and 2.2.9, ADR-001. Items marked **(assumption)** are not fixed by PA1 and need team confirmation before baseline-pa2.

## 5.1 Functional Requirements – F05 and F06 (Table 3)

| ID       | Requirement                                                                                                                                                                                                                                                                              | Feature | Priority | Source                                |
| :------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------ | :------- | :------------------------------------ |
| FR-05-01 | The system shall let a signed-in user select a room and a date and display the schedule of that room for that date. The default date shall be today in UTC+7.                                                                                                                            | F05     | Must     | PA1 §2.4 (F05)                        |
| FR-05-02 | The system shall list every approved booking of the selected room on the selected date in ascending order of start time, showing the start time and the end time of each. If there is none, the system shall state that the room has no approved bookings that day.                      | F05     | Must     | PA1 §2.4 (F05); WBS 2.2.6             |
| FR-05-03 | The system shall show only approved bookings on the schedule. Pending, rejected and cancelled bookings shall not appear, and a booking cancelled before its start time shall disappear from the schedule at once.                                                                        | F05     | Must     | PA1 §2.4 (F05, F07)                   |
| FR-05-04 | The system shall display the name, the capacity and the availability status of the selected room on the schedule page.                                                                                                                                                                   | F05     | Must     | PA1 §2.4 (F02, F05); WBS 2.2.6        |
| FR-05-05 | The system shall display the free periods of the selected date, that is, the periods not covered by approved bookings, so that users can identify suitable free periods.                                                                                                                 | F05     | Should   | PA1 §2.4 (F05)                        |
| FR-05-06 | The system shall show the requester name and the purpose of a booking only to the Resource Managers of that room and to Admins. Other Borrowers shall see only the time slot marked as booked. **(assumption)**                                                                          | F05     | Should   | Team assumption; PA1 §2.3 (roles)     |
| FR-06-01 | The system shall let a Borrower submit a booking request for one room on one date, with a start time, an end time, a purpose and a headcount. All fields are required, and the start time and the end time shall fall on the selected date.                                              | F06     | Must     | PA1 §2.4 (F06); WBS 2.2.6             |
| FR-06-02 | The system shall reject a booking request whose end time is not later than its start time.                                                                                                                                                                                               | F06     | Must     | PA1 §2.4 (F06)                        |
| FR-06-03 | The system shall reject a booking request whose start time is not later than the current time in UTC+7.                                                                                                                                                                                  | F06     | Must     | PA1 §2.4 (F06); PA1 §5 risk 2         |
| FR-06-04 | The system shall reject a booking request whose headcount is not a whole number of at least 1, or is greater than the capacity of the room.                                                                                                                                              | F06     | Must     | PA1 §2.4 (F06)                        |
| FR-06-05 | The system shall reject a booking request whose time range overlaps an approved booking of the same room. Time ranges are half-open, so a booking that ends at the start time of another does not overlap it. Pending requests do not block each other; approval rechecks overlap (F07). | F06     | Must     | PA1 §2.4 (F06, F07); ADR-001          |
| FR-06-06 | The system shall not accept a new booking request for a room that is under maintenance or unavailable. The interface shall disable the booking action, and the backend shall reject the request even when it is sent directly to the API.                                                | F06     | Must     | PA1 §2.4 (F02, F06); WBS 2.2.6, 4.2.6 |
| FR-06-07 | The system shall save a valid booking request with status Pending, linked to the requester and the room, and show it to the requester and to the Resource Managers assigned to that room.                                                                                                | F06     | Must     | PA1 §2.4 (F06, F08)                   |
| FR-06-08 | The system shall take the requester identity from the authenticated session and accept booking requests only from the Borrower role.                                                                                                                                                     | F06     | Must     | PA1 §2.4 (F01)                        |
| FR-06-09 | When a booking request fails validation, the system shall show a message that names the field and the rule that failed, and shall keep the values the user entered.                                                                                                                      | F06     | Should   | PA1 WBS 3.3.4 (error messages)        |

Open points for the team:

1. FR-05-06: should Borrowers see who booked a slot? The draft hides it.
2. PA1 sets no opening hours, step size, minimum or maximum duration, or advance-booking limit for rooms. The draft adds none; add them as new requirements only if the team agrees.
3. FR-06-05: pending requests do not reserve the room. Only approval (F07) does.

## 5.2 Non-Functional Requirements (Table 4)

| ID     | Category                  | Requirement (measurable)                                                                                                                                                                                                                                                                                                                                     | How it will be verified                                                                                                                                                                                                        |
| :----- | :------------------------ | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| NFR-01 | Performance               | Under 200 concurrent users on the reference data set (50 resources, 20 rooms, 5,000 loan and booking records), read operations (catalogue search, room schedule, own request list) shall respond in ≤ 1.0 s at P95, measured at the API from one client on a stable broadband connection after a warm-up of 10 requests. **(assumption: load and data set)** | JMeter test plan with 200 threads, 2-minute ramp-up and 10-minute steady state against the staging deployment loaded with the reference data. Read P95 from the aggregate report. Run in WBS 6.1.6.                            |
| NFR-02 | Performance               | Under 50 concurrent users, write operations (submit a loan or booking request, approve, cancel) shall respond in ≤ 2.0 s at P95, under the same data set and measurement conditions as NFR-01. **(assumption)**                                                                                                                                              | JMeter mixed write scenario with 50 threads, 5-minute steady state, same environment as NFR-01. Read P95 per operation from the aggregate report.                                                                              |
| NFR-03 | Security                  | The server shall check authentication, role and ownership or assigned-resource scope on 100% of protected endpoints. A request without a session shall get 401, and a request outside the role or scope shall get 403. Hiding controls in the interface shall not be the only protection.                                                                    | Automated authorization matrix test run in CI: every endpoint × Borrower, Manager of the resource, Manager of another resource, Admin and anonymous caller, using direct API calls. All cells must match the permission table. |
| NFR-04 | Security                  | Passwords shall be stored only as bcrypt hashes with cost ≥ 10. The session token shall be a JWT in an `HttpOnly` and `Secure` cookie that expires within 24 h. No plaintext password or token shall appear in the database, in logs or in the repository.                                                                                                   | Inspect the stored hashes and the `Set-Cookie` header in an E2E test; review logging code; search the repository and its history for secrets before each baseline tag.                                                         |
| NFR-05 | Security                  | A deactivated account shall be rejected on its next request (401), even when its token has not expired.                                                                                                                                                                                                                                                      | E2E test: sign in, deactivate the account as Admin, repeat a protected call with the old cookie and expect 401.                                                                                                                |
| NFR-06 | Security                  | All production traffic shall use HTTPS. The backend shall validate every input: invalid or oversized input shall get a 4xx response and never a 5xx response. An OWASP ZAP baseline scan of the staging deployment shall report 0 High-risk alerts.                                                                                                          | OWASP ZAP baseline scan on staging before the PA5 release; negative API tests that send invalid, missing and oversized fields; check that HTTP is redirected to HTTPS.                                                         |
| NFR-07 | Availability, reliability | The system shall be available ≥ 99.0% of the time during working hours 07:00–22:00 UTC+7 over the period from first deployment to the PA5 demo, excluding maintenance announced at least 24 h ahead. **(assumption: working hours, free-tier hosting)**                                                                                                      | External uptime monitor calling a health endpoint every 5 minutes. Uptime = successful checks ÷ all checks inside the working-hours window, taken from the monitor logs.                                                       |
| NFR-08 | Availability, reliability | The database shall be backed up at least daily. After a data loss, service shall be restored in ≤ 2 h (RTO) with at most 24 h of data lost (RPO). **(assumption: the Supabase plan must allow backups; PA1 risk 8 requires them)**                                                                                                                           | Restore a backup into a new database, measure the elapsed time and compare record counts with the source. Record the result and any plan limitation.                                                                           |
| NFR-09 | Availability, reliability | When 20 concurrent approvals compete for the same room time slot, or for the same equipment item, at most one shall succeed; the others shall receive a conflict error and stay pending. After the test there shall be 0 overlapping approved bookings and 0 double-reserved items.                                                                          | Concurrency test (WBS 6.1.4): 20 parallel approval calls, repeated 10 times. After each run, query the database for overlapping approved bookings and for items with more than one active reservation.                         |
| NFR-10 | Usability                 | The interface shall work without horizontal scrolling from 360 px to 1920 px screen width, and in the latest two versions of Chrome, Edge, Firefox and Safari.                                                                                                                                                                                               | Checklist run on sign-in, catalogue, room schedule, booking form and request list at 360, 768 and 1920 px in each browser.                                                                                                     |
| NFR-11 | Usability                 | The key screens (sign-in, catalogue, room schedule, booking form, request list) shall meet WCAG 2.1 AA basics: text contrast ≥ 4.5:1, a visible label on every field, all booking-form functions operable by keyboard in a logical Tab order, and error messages that name the field and the fix.                                                            | Lighthouse or axe accessibility score ≥ 90 on each key screen, a contrast check on mockup colours, and a manual keyboard-only walkthrough of the booking flow. Results go to the §8 accessibility audit.                       |
| NFR-12 | Usability                 | At least 4 of 5 first-time Borrowers shall submit a valid equipment or room request within 3 minutes at the first attempt, without help. **(assumption: participants are students who have not seen the system)**                                                                                                                                            | Moderated test with 5 students on the prototype (later the application): one scripted task, no hints, stopwatch time and success recorded per participant.                                                                     |

Notes:

1. NFR-01 to NFR-12 give the measurement conditions required by the template. PA2 specifies how each is verified; the runs themselves belong to WBS 4.2.9 (test design) and 6.1.6 (execution).
2. The 360 px lower bound follows PA1 §3.3. The load figures (200 and 50 users, reference data), 24 h token lifetime, uptime target, RTO and RPO come from the team task list and are assumptions until the team confirms them. If hosting limits make a figure unrealistic, change the figure and record the change in §10.
3. Time handling (UTC+7 display, `timestamptz` storage) follows ADR-001 and is tested under FR-06-03 and FR-06-05, not as a separate NFR.
